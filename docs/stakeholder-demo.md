# RAMP Mobile Concept: stakeholder demonstration

**Status: independent, unofficial prototype.** Do not present the demonstration as
approved by RAMP or describe sample data as live. This is for a discovery meeting
with Tina and Autumn only, unless RAMP authorizes wider sharing.

## Purpose (15–20 minute demonstration)

Show how the existing RAMP Approved web directory could become an accessible,
helpful iPhone/Android experience rather than a thin website wrapper.

## Walkthrough

1. **Start in Explore**: explain that the offline sample has nine public
   directory entries. Demonstrate search for "Providence" and filters for city,
   category and accessibility *topics mentioned*, not guaranteed features.
2. **Open a location**: read actual directory notes, including cautions about
   narrow restrooms and access limitations. Explain that suitability must always
   be confirmed with the venue.
3. **Plan a visit**: toggle the private four-question preparation checklist,
   save the location, then demonstrate sharing its address and opening external directions.
4. **Open the Map tab**: switch between "Map and list" and "List only". The map
   does not ask for GPS access. Sample addresses intentionally do not generate
   unverified pins. Once RAMP verifies coordinates, that same tab can display them.
5. **Open Resources**: show links to RAMP's existing assessment and scheduling
   workflows as an initial bridge to the website.
6. **Discuss a future live feed**: a strict, approval-gated adapter exists in
   code and is disabled by default. Explain publication/unpublishing,
   source attribution and data update responsibilities.

## Five client decisions needed before scope / pricing

1. Who is the primary first-release user: accessible-place seekers, venue
   owners, assessors, administrators, or multiple groups?
2. Which functions must be native at launch: browse/map, favorites,
   accessibility reports, self-assessments, new venue submissions and bookings?
3. What is the authoritative directory backend today? Who owns it and can
   provide documented, approved read-only access and verified coordinates?
4. Who controls Apple/Google developer accounts, trademarks, permissions,
   ongoing data edits, privacy and support?
5. What are the target pilot date, budget and ongoing maintenance expectations?

## Do not promise

- That all nine sample venue listings are currently verified or current.
- That map pins will appear before valid, permissioned coordinate data exists.
- That the app has passed a physical-device accessibility audit.
- That a TestFlight/Google Play build or store submission has occurred.
- That a "topic mentioned" filter is an ADA or accessibility certification.

## Suggested closing

"We can agree on a first-release scope, verify who maintains the current
directory, and conduct user accessibility testing before deciding how much
of the assessment and approval workflow belongs inside the app."

## After the call

Obtain written authorization and scope, then connect the source of truth,
test with people using screen readers, verify map/location provenance,
generate internal build artifacts and plan Apple/Google review.
